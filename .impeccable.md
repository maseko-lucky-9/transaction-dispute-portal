# Design context — Transactions Dispute Portal

Read this before any design work in this repo. It overrides the generic aesthetic rules in the
`impeccable` skill wherever the two disagree — see **Locked constraints**.

## Design Context

### Users

Two roles, one product, one component set.

**Customer** (primary). A Capitec retail banking customer who has spotted a transaction they do
not recognise. They arrive worried, often on a phone, sometimes late at night, and the money has
already left the account. Their job: find the transaction, say what is wrong with it, then know —
without asking anyone — where the dispute stands. Designed for first, and wins when the two roles
conflict.

**Agent** (secondary). A back-office reviewer working a queue for a whole shift on a desktop.
Their job: scan many rows, open one dispute, read the evidence, move it to the next state. Density
and scanning speed matter, and yield to the customer on shared components.

**Assessor** (incidental). This is an SE3 take-home, so a hiring reviewer reads the code and clicks
the UI. Not a design audience — never trade a user's clarity for something that only reads well in
a screenshot.

### Brand Personality

Capitec, in three words: **plain-spoken, exact, unhurried.**

- *Plain-spoken* — short sentences, no banking register. "Under review", not "Pending adjudication".
- *Exact* — amounts, dates, references and states are stated precisely, never rounded, abbreviated
  or decorated. Accuracy is the product.
- *Unhurried* — nothing pulses, counts down or nags. A disputed R4 300 is stressful enough.

Emotional target: **reassurance through visible precision.** The customer should feel that someone
competent has the matter in hand. Delight is not the goal here; calm is.

### Aesthetic Direction

**Direction A, "Crimson Pill"** — chosen, built, shipped. Floating white header with pill
navigation, crimson reserved for the one main action per page, Blue Gem for links, Royal Blue as a
large-fill panel on the landing page.

The four rejected directions remain in `docs/design/brand-mockups/` as the record of what was
considered: B Gem Sidebar, C Compact Ledger, D Royal Dashboard, E Soft Canvas. Open
`docs/design/brand-mockups/index.html` before proposing anything structural — the question may
already be answered there.

Both themes are first-class. Every token is a `light-dark()` pair, the page follows
`prefers-color-scheme` with no JavaScript, and the header toggle pins
`<html data-theme="light|dark">`. Any new colour ships as a pair and is checked in a real browser in
both themes.

Anti-references: **a fintech dashboard** — no sparklines, no hero metric, no gradient hero, no
spend-insight cards; this product has no analytics and the API returns no totals. **A legacy bank
portal** — no dense grey chrome, no modal stacks, no jargon.

### Design Principles

1. **The brand is settled; the craft is in the detail.** Palette, radii, card treatment and
   direction A are decided. New work earns its quality through spacing rhythm, typographic
   hierarchy, state coverage and copy — not by reopening the palette.
2. **One crimson action per page.** Crimson is the single primary action. Everything else is
   secondary, ghost or a text link. A second crimson button on a page is a bug.
3. **Status is the spine of the product.** Five dispute states and three transaction states, each
   with a fixed foreground/background token pair. Status is always a pill with a word in it — never
   colour alone, never an icon alone.
4. **Never invent a number.** The API pages results and returns no totals, so no counts on filter
   links and no totals on Home. If a figure is not in the response, it does not appear.
5. **Both themes, or it is not done.** Verified in a real browser (`playwright-cli`), light and
   dark. jsdom cannot run axe's contrast rule.
6. **Every surface has four states.** Loading (skeleton), empty (teaches the next action), error
   (`ErrorState`, carrying the trace reference) and populated. A screen with only its populated
   state is unfinished.
7. **Customer first on shared components.** When the agent queue wants more density than the
   customer's table, the customer's reading wins and the agent gets the difference locally.

## Locked constraints

These override the `impeccable` skill's generic rules. The skill's aesthetic rules bind **surfaces
that do not exist yet**, not the system below.

| Locked | Why |
|---|---|
| Hex colour values in `frontend/src/index.css` | The Capitec palette is supplied as hex. Not to be converted to OKLCH. |
| `#ffffff` cards and `--card` | The supplied Capitec logo file has a white background and sits on a white tile. |
| `--shadow-card`, `--radius-card`, `TableCard` | The card treatment of direction A. |
| The five dispute and three transaction status token pairs | Contrast-verified in both themes. |
| `--brand-royal` as fill and large text only | White on it is 4.48:1 — fine at >= 24px (or >= 19px bold), not a small-text pair. |
| The "what every direction keeps" rules | Bottom section of `docs/design/brand-mockups/index.html`. Still binding. |

Accessibility target: **WCAG AA, 4.5:1**, both themes — and it is enforced, not aspirational:

- `frontend/src/lib/contrast.test.ts` parses `index.css`, extracts every `light-dark()` pair and
  asserts >= 4.5:1 for each listed text/background pair in **both** themes. **A new colour token
  that carries text must be added to its `PAIRS` list**, or it is silently unverified.
- `frontend/src/a11y.test.tsx` runs `vitest-axe` over the real screens for structure.
- jsdom has no layout, so axe's `color-contrast` rule cannot run there. Composed contrast —
  translucent fills, hover and transition states, text over the Royal Blue panel — is a real-browser
  check (`playwright-cli`), light and dark. This is how `bg-primary/90` was caught dropping
  white-on-crimson below 4.5:1 mid-transition (`frontend/src/components/ui/button.tsx:12`).

### Two hard technical constraints on any design change

- **CSP is `font-src 'self'`** (`frontend/nginx/csp-app.conf`). No Google Fonts, no CDN. Any
  webfont is a self-hosted `woff2` served from the app origin.
- **The sign-in page is Keycloak's, and its theme lives in two repos.** Editing
  `deploy/keycloak/themes/dispute-portal/login/` requires byte-identical files in
  `maseko-lucky-9/homelab-infra` under `apps/dispute-portal/keycloak-theme/`, or `ci-ok` fails on
  drift (ADR-018, `scripts/check-keycloak-theme-sync.sh`). A brand change that must also appear on
  the sign-in page is therefore a two-repo change. A *new* theme file additionally needs a `files:`
  line and a mount in homelab-infra.

## Open decisions

**Typography — one self-hosted display face, face not yet chosen.** Decided: headings and currency
figures get a single self-hosted display face; body, tables and form labels keep the existing
`system-ui` stack, recorded here as a deliberate choice rather than an oversight. Constraints on the
pick: self-hosted `woff2` under ~40KB, true tabular lining figures (this product is mostly amounts
and dates), a usable 600-700 weight, and a licence permitting self-hosting. Not Inter, DM Sans,
Instrument, Plus Jakarta, Fraunces, Playfair, IBM Plex or Space Grotesk. Mirror into the Keycloak
theme only if the sign-in page should carry it too.
